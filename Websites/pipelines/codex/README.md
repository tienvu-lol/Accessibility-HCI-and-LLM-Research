# Codex pipeline — slots 04–06

Thirty-six replicas across twelve categories: university, healthcare, company, e-commerce, news, government, fashion, weather, nonprofit, church, portfolio, restaurant. Claude has slots 01–03, Codex 04–06, open-source 07–10. Portfolio and restaurant joined this pipeline on 2026-11-13. Portfolio slots 04–06 were already delivered before this queue existed and their directories were renamed that day from `01-rowan-ellis`/`02-jamie-vale`/`03-avery-north` to `PORT-04`/`PORT-05`/`PORT-06` for `MODEL_ALLOCATION.md` §5. Restaurant slots 04–06 are unbuilt: its pre-protocol batch was deleted on 2026-11-13.

This is a **configuration and task-preparation pipeline**, operated through a Codex session. It does not call an API, invoke an assumed CLI, launch agents, create worktrees, generate sites, or publish automatically. No service credentials or API keys are required. The prepared brief is handed to the generation session explicitly, one replica at a time. This keeps the setup independent of Claude's provider-specific orchestration.

## Files

| Path | Purpose |
| --- | --- |
| `config.json` | Fixed allocation, shared paths, approval policy, execution limits, declared model/runtime |
| `categories.json` | Twelve categories, ten slot strata each, conditional pages/interactions, simulation restrictions |
| `schemas/config.schema.json` | Strict configuration schema; scripts validate the subset used here without dependencies |
| `prompts/` | Independently authored research, build, and QC-correction instructions |
| `research/` | Codex source evidence; no fabricated research or source approval is prefilled |
| `queue/manifest.json` | Twelve research tasks and thirty-six build tasks, with dependencies |
| `scripts/validate.mjs` | Configuration and optional per-site readiness checks |
| `scripts/prepare-task.mjs` | Exact brief preview or recorded brief with immutable input snapshots |
| `scripts/record-qc.mjs` | Executes the shared QC and records real output/exit status in an existing run |
| `scripts/lib.mjs` | CSV parsing, schema checks, paths, inventory and allocation validation |
| `tests/pipeline.test.mjs` | Node built-in tests using temporary synthetic fixtures; no site generation |
| `runs/<run-id>/` | Exact task, declared attribution, protocol/source snapshots, QC evidence and handoff |

## Initial state

All 40 tasks are **planned**, not running. No sources are chosen, approved, or generated by this setup. Central inventory templates contain ten allocated IDs per category with blank source/verification/approval fields. Existing Claude research has not been silently promoted to approved central records. `assignments.csv` and Claude files are unchanged.

Model ID/version/runtime/operator are initially null. The user did not specify an exact generation model, so none is invented. Before a build, declare the actual model and runtime in config.json or with the task command flags; synchronize the approved assignment/inventory accordingly. A declaration is not independently authenticated by these scripts. Do not insert credentials into these fields.

Other-group strata in categories.json are coordination proposals for completing the required ten-slot category plan. Codex slots 04–06 mirror the three broad Claude strata using different reference sites. Reconcile other slots with the project coordinator and approved central inventory before generation. This file does not change another group's pipeline. Source difficulty, browsing access, budget, retries, and interventions remain important study controls.

## Commands

Run from the repository root (`Accessibility-HCI-and-LLM-Research`). Requires a modern Node.js runtime with built-in test support; Node 20+ is the intended baseline. No npm install is needed for pipeline configuration/preparation.

```sh
node Websites/pipelines/codex/scripts/validate.mjs
node --test Websites/pipelines/codex/tests/pipeline.test.mjs
```

Preview a research brief (stdout only):

```sh
node Websites/pipelines/codex/scripts/prepare-task.mjs research UNI
```

Record it instead, including protocol/config/inventory snapshots:

```sh
node Websites/pipelines/codex/scripts/prepare-task.mjs research UNI --record
```

Preparation does not execute the brief or update queue/assignment statuses. Hand the generated `task.md` to the actual Codex session when ready to do research. Follow its write boundaries; use the assigned research file and central inventory format.

### Source coordination and approval

1. Research only Codex's three slots. Reserve sources centrally and reconcile Claude/open-source choices; do not copy their generation prompts or code.
2. Complete `Websites/metadata/source-inventories/<category>.csv` for all ten distinct references, including actual model IDs, page scopes, evidence and verification limitations. See that directory's README for the CSV contract.
3. Obtain project-lead approval for the complete category scope and assignments under the shared rules. Fill approval date/person/evidence only from that actual decision. Claude's waiver is not inherited.
4. Synchronize source URL, model ID/version and approval date in `metadata/assignments.csv`; the coordinator owns other groups' rows. Retain durable evidence and log changes.
5. Only then prepare a build. Readiness is scoped to the model group being built: a Codex build requires Codex's three rows to be complete, verified, approved and synchronized with the register, and is not blocked by incomplete Claude or open-source rows. A missing or unverified reference, missing model, drifted assignment or missing approval on a Codex row still blocks preparation, as does a Codex URL that duplicates any other row in the category. There is no fallback source picker in Phase B. The category's **active allocation** is slots 01–06 (`MODEL_ALLOCATION.md` section 2); open-source slots 07–10 are deferred and require no approval while inactive, so coordinating them is not a precondition for a Codex build.

### Prepare one build

Replace the uppercase argument values below with the actual recorded model/runtime/operator; they are placeholders, not model recommendations.

```sh
node Websites/pipelines/codex/scripts/validate.mjs --ready UNI-04 --model ACTUAL_MODEL_ID --runtime ACTUAL_RUNTIME --operator OPERATOR_NAME
node Websites/pipelines/codex/scripts/prepare-task.mjs build UNI-04 --model ACTUAL_MODEL_ID --runtime ACTUAL_RUNTIME --operator OPERATOR_NAME --record
```

Optional `--model-version VERSION` records an identifiable release/version. If supplied, it must match the approved inventory. Unknown version may remain null; unknown critical model attribution may not be fabricated. Config-declared values can replace flags.

A recorded task contains:

```text
runs/<run-id>/
├── task.md                 Exact prompt and task context
├── run.json                Prepared state, declared attribution, hashes, null generation timestamps
├── snapshots/              Copies of rules, allocation, config, categories, prompt, inventory, register
└── handoff.md               Record actual execution and delivery here
```

Each snapshot's original path and SHA-256 are in run.json. Do not overwrite these inputs after preparing a task; create another run if approval/model/scope changes. Existing website output is never silently overwritten by build preparation.

Execute the task explicitly in a Codex session. The site goes under `Websites/<category>/codex/<ID>/`, with the shared protocol's required files. Set actual generation timestamps and tool/budget/retry details when execution happens. Prepared timestamps are not generation timestamps. Preserve initial output separately before QC corrections if the study analyzes raw versus corrected output.

### QC and correction

The common evaluation tool is separate from the generated websites. Install its locked dependencies if necessary:

```sh
cd Websites/tools/qc
npm ci
```

Return to the repository root, then record actual shared QC for a generated site and its matching recorded build/repair run:

```sh
node Websites/pipelines/codex/scripts/record-qc.mjs UNI-04 --run RUN-ID
```

This runs the existing `qc.js` with a JSON report path. It retains stdout/stderr and the actual exit status, tool hash and timestamps. A dependency/browser failure is recorded as failure/unavailable, not a pass. The wrapper does not install or change the evaluation environment automatically. The initial setup did not run website QC because no new sites exist.

For a failing report, prepare a separate correction task:

```sh
node Websites/pipelines/codex/scripts/prepare-task.mjs repair UNI-04 --model ACTUAL_MODEL_ID --runtime ACTUAL_RUNTIME --operator OPERATOR_NAME --qc runs/RUN-ID/qc-TIMESTAMP.json --record
```

`--qc` is relative to pipelines/codex, must identify this site and contain actual failures, and is copied into the repair snapshots. This is generation-stage QC correction, distinct from later experimental accessibility repair treatments. Interaction checks, visual fidelity, keyboard review and human acceptance are separate from an initial-page axe pass.

## Coordination and acceptance

- Queue is execution bookkeeping; assignments.csv is dataset state. Update both intentionally after real transitions. Never infer “generating” from task preparation or “accepted” from QC alone.
- Default concurrency is **one**. Preparation checks the queue's declared running builds against the configured limit (maximum configurable: three). Because no executor is launched, this is not a process lock or automatic resource scheduler. The operator must keep running-state records current and hand off no more than the declared limit. Use isolated checkouts if parallel execution is later introduced.
- After a real delivery, update only the corresponding Codex assignment row and append the central change log. Keep any other-group changes with the coordinator. A human reviewer decides acceptance.
- No automatic commit, push, publication, approval, or unbounded retry loop. Use separate recorded runs for retries/corrections.
- Keep run.json, task.md, handoff.md, input snapshots and QC JSON as provenance where repository policy permits. Raw logs/screenshots are ignored by default; archive them privately if needed, avoid secrets, and record the evidence location.

## Verification

The setup's thirteen tests cover CSV edge cases, configuration/allocation integrity, path boundaries, per-group approval scoping, cross-group source duplication, assignment drift, model attribution, declared concurrency, task snapshot creation without execution, existing-output protection, and invalid CLI/repair inputs. Synthetic test sources are confined to temporary directories and deleted afterward. Passing pipeline tests does not mean any websites have been generated, their references approved, or browser QC completed.
