Twelve small tools I built instead of one large one

May 12, 2026 11 min read by Tobias Quill toolingcraft

In early 2025 I scoped a tool that would have taken a year: one interface over every part of my workflow, with a plugin system, because of course it had a plugin system. I wrote the proposal, read it back, and built something else that weekend instead.

What twelve small tools looks like

Nine weekends later there were twelve programs, none longer than 400 lines, each doing one thing with a text file. A commit grouper. A queue for the plotter. A contrast checker that only handles the four colours I use. A thing that renames photographs. Seven of the twelve are still in daily use; the other five did their job and were deleted, which the large tool would never have permitted.

  • Every tool reads and writes plain text, so any of them can feed any other.
  • No tool has configuration. If I need different behaviour, I copy the file and change it.
  • Each one is a single file with its usage notes in the first comment block.
  • None of them have tests, because all of them are observable in one run. This is a confession, not advice.

Why the large one would have failed

Not because large tools are bad. Because the plugin system was load-bearing for a workflow I had not yet discovered, and I would have spent the year building the system rather than finding out what the workflow was. The twelve small ones told me, by which ones I kept.

“The large tool was going to take a year. The twelve small ones took nine weekends.”

The one I would still like to build is the thirteenth: something that notices when two of the twelve are always run together. I have been meaning to write it for eight months, which is itself an answer.
